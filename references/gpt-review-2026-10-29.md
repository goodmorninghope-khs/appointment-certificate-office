제공한 화면·코드 기준으로, 발급 전 표시·수령코드 분리·취소 상태 조회는 좋은 출발입니다. 다만 현재의 ‘승인’은 성명 입력이며, ‘진위확인’은 저장된 기록과의 대조입니다. 실제 결재와 문서 자체의 진위 보장까지 갖춘 것으로 보기는 어렵습니다. 발급대장 0건인 지금, 아래 ‘즉시’ 항목부터 정리하는 것이 좋겠습니다.

우선순위는 ‘즉시=실제 개인정보·직인을 넣기 전’, ‘다음=시범운영 단계’, ‘나중=부서 확산 단계’입니다.

### 3. 보안·진위확인 설계

- [즉시] 현재: 편집 권한 여부로 담당자 구분 → 제안: 기관 인증과 서버 권한검사로 기안·승인·발급·관인관리 권한을 분리 → 이유: 화면 버튼을 숨기는 것만으로 DB 직접 접근을 막을 수 없음.
- [즉시] 현재: 공개 컬렉션에 코드로 암호화한 사본 저장 → 제안: 공개 목록 읽기를 막을 수 있는 서버 조회 구조로 전환하고 요청 횟수를 제한 → 이유: 암호문을 확보하면 오프라인 코드 대입이 가능하며 PBKDF2만으로 이를 차단할 수 없음.
- [즉시] 현재: 진위코드는 내용 해시의 앞 8자리, 약 32비트 → 제안: 서버가 생성하는 충분히 긴 무작위 조회 토큰을 사용하고 암호 기능 실패 시 발급 중단 → 이유: 현재 코드는 비밀키 없는 짧은 해시여서 발급기관을 인증하지 못하고, 약한 대체 해시까지 허용함.
- [즉시] 현재: 수령 사본에 `sealImage`와 진위코드 포함 → 제안: 원본 직인 파일·내부 필드를 제거한 최소 결과물만 전달 → 이유: 수령 권한이 재사용 가능한 직인 원본의 배포 권한까지 뜻하지는 않음.
- [즉시] 현재: 번호 조회 후 `set()`으로 저장하고 공개 사본은 나중에 생성 → 제안: 서버 트랜잭션·중복요청 방지키·발급 완료 상태를 도입 → 이유: 동시 발급 시 덮어쓰기와 ‘대장은 있는데 수령이 안 되는’ 부분 실패를 막아야 함.
- [다음] 현재: 조회 결과는 이름을 가린 발급 기록 → 제안: ‘등록 사실 확인’임을 명시하고 공식 도메인에서 현재 상태·발급 내용을 대조하도록 제공 → 이유: 정상 코드를 다른 이미지에 붙여도 현재 방식으로는 이미지 위조를 판별하기 어려움.
- [나중] 현재: PNG와 발급 기록이 분리 → 제안: 최종 파일 해시와 기관 전자서명을 연계하고 검증 도구 제공 → 이유: 등록 사실을 넘어 제출된 파일의 변경 여부까지 확인할 수 있음〔확인 필요: 적용할 전자서명 방식·기관 인증체계〕.

### 4. 확장 — 일괄 발급·다른 부서 재사용

- [다음] 현재: 한 명씩 입력 → 제안: CSV·엑셀 업로드 후 열 매핑·필수값·중복·임기 오류를 검증하고 전체 미리보기 제공 → 이유: AI파트너즈 일괄 발급에서는 입력 속도보다 오류를 한 번에 찾는 능력이 중요함.
- [다음] 현재: 건별 발급·전달 → 제안: 승인된 명단을 배치로 고정하고 성공·실패·미전달 건을 구분해 실패 건만 재시도 → 이유: 재실행으로 중복 발급하거나 일부 대상자를 빠뜨리지 않아야 함.
- [다음] 현재: 기관 기본값 한 묶음과 연도별 번호 사용 → 제안: 기관·부서·위원회·문서 종류별 설정과 번호 정책을 분리하고 이전 버전 보존 → 이유: 부서가 늘어나도 권한·번호·서식이 섞이지 않게 해야 함.
- [나중] 현재: 공통 설정 저장 → 제안: 중앙에서 승인한 서식·관인·보안 기준과 부서가 바꿀 수 있는 문구를 구분 → 이유: 재사용성을 높이면서 부서의 설정 실수가 다른 부서에 번지는 것을 막을 수 있음.
- [나중] 현재: 발급 건수 중심 대장 → 제안: 미수령·임기 만료 예정·정정·취소 현황을 업무 화면으로 제공 → 이유: 발급소가 위원 관리 업무까지 연결될 수 있음.

### 재사용 가능한 SKILL.md에 꼭 넣을 원칙 5개

1. **AI는 초안을 만들고, 권한 있는 사람이 확정한다.** 공식 결재 근거와 승인된 내용을 확인한 뒤 발급한다.
2. **개인정보와 관인은 최소한으로 다룬다.** 실제 개인정보·직인·인증정보를 스킬 본문이나 예시 파일에 넣지 않는다.
3. **실패하면 발급을 멈춘다.** 인증·저장·암호화·번호 확보 실패를 임시 발급이나 약한 대체 방식으로 우회하지 않는다.
4. **발급 사실을 재구성할 수 있게 남긴다.** 승인 내용·최종본·버전·처리자·시각·정정 및 취소 이력을 연결한다.
5. **완료 기준을 끝까지 검증한다.** 발급 버튼 성공에 그치지 않고 대상자 수령·진위조회·취소 반영·동시 발급·장애 후 재시도까지 확인한다.

## Aside 코드 대조 메모 (GPT 지적이 코드와 맞는지)

| GPT 지적 | 코드에서 확인한 사실 | 판단 |
|---|---|---|
| 승인은 성명 입력뿐 | 체크 3개 + `f-approver` 텍스트만으로 승인 버튼 활성화 | 맞음 |
| 진위코드 약 32비트 | `codeFor()`가 SHA-256 결과 앞 8자리 사용, 실패 시 FNV 해시로 대체 | 맞음 |
| db 없어도 발급 진행 | db가 없으면 `pubLocal`(화면 메모리)에 저장하고 발급 완료 처리 | 맞음 |
| 수령 사본에 직인 원본 포함 | `RECEIPT_KEYS`에 `sealImage`, `code` 포함 | 맞음 |
| 저장 공간 부족 시 기록 정리 안내 | quota_exceeded 오류 문구가 "오래된 기록을 정리한 뒤 다시 시도" | 맞음 |
| 번호 조회 후 set, 공개 사본은 나중 | `registerIssue()`가 get→set(트랜잭션 아님) 후 `publishPublic()` 호출 | 맞음. 공개 사본 생성 실패 시 대장에만 남는 부분 실패 가능 |
| 승인 시 폼을 다시 읽음 | 승인 버튼에서 `readForm()` 재호출. 다만 2단계에서는 입력 폼이 숨겨져 실제 수정 경로는 좁음 | 부분적으로 맞음(위험 낮음) |
| 취소가 두 번 클릭 | "한 번 더 누르면 취소" 4초 확인, 사유 저장 없음 | 맞음 |

## 우선 고칠 순서 (Aside 제안)

1. 예시값(홍길동·한빛구·김한빛) 남은 채 검토 요청 차단, db 미연결 시 정식 발급 차단
2. 수령 사본에서 `sealImage` 제외, quota 오류 문구를 "발급 중단, 담당자 문의"로 변경
3. 결재문서 번호·결재일 칸 추가, 취소 사유·구분(발급 오류/해촉/임기 만료) 추가
4. AI파트너즈용 일괄 입력(CSV 붙여넣기 → 검증 → 한 건씩 발급)
5. 공식 운영 전: 서버 조회·권한 분리·조회 횟수 제한·긴 무작위 토큰(기관 정보화 담당과 협의)
